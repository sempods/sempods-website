## Editorial decision

Rewrite the positioning and Start journey, with supporting changes across the existing pages.
Keep the live demonstration, visual identity and current URLs. The evidence calls for content and
entry-point changes; it does not establish a need for a new visual design.

Use **owner-controlled linked data that different clients can use** as the organizing idea.
Explain Contexts as the current contract and Kotlin authorization mechanism in the technical
pages. Keep the broader direction visible without presenting it as released behavior.

The three directional questions have different answers:

- **Contexts become optional:** not adopted in the selected normative snapshot. The
  [vision at the selected revision](https://github.com/sempods/sempods-spec/blob/10d91f307ad91c9bdca16e037b4088c27be49dbf/docs/vision.md)
  and [data-access proposal](https://github.com/sempods/sempods-spec/blob/10d91f307ad91c9bdca16e037b4088c27be49dbf/docs/proposals/data-access.md)
  distinguish the direction from current requirements. Ordinary access without Context setup is
  proposed; Context discovery/selection remains core even in that proposal. Context lifecycle
  management is already optional. Avoid “Contexts are optional in 0.2”.
- **Kotlin becomes a building kit:** supported by the
  [released modularity guide](https://github.com/sempods/sempods-kotlin/blob/v0.2.0/docs/concepts/modularity.md#deployment-and-upgrades).
  Distinguish client libraries, embeddable services and a development/evaluation composition.
  The supplied composition has no supported upgrade path. Fixed distributions with update
  mechanisms remain future work, not a current download promise.
- **Specification and implementation are independent:** supported by
  [selected governance](https://github.com/sempods/sempods-spec/blob/10d91f307ad91c9bdca16e037b4088c27be49dbf/GOVERNANCE.md#what-the-tag-changes-and-what-it-no-longer-does).
  Normative development text already determines the contract. Kotlin's existing behavior does
  not override it. Kotlin 0.2.0 is not a specification 0.2 release.

Editorial brief: a visitor wants useful data without giving each app ownership of it. Show a
real pod, follow its linked resource, explain the shared authorized interface, then offer three
paths: build a client, implement the contract, or compose/run a pod. More detailed permission
mechanisms come after that shared idea.

Possible English copy, for the later whole-page rewrite:

> Keep your data where you control it. Let apps and agents come to it.

> sempods brings linked data, queries and authorization into one open pod contract.
> Different implementations can give clients the same way in.

> Build against a pod, implement the contract, or compose your own server from the Kotlin modules.

These are editorial candidates, not replacement paragraphs approved or published in isolation.

## Example and installation gaps

`src/data/coordinates.ts` still selects 0.1.0. `start.astro:172` names `SempodsPodClient`, removed
in 0.2. The released client guide supplies tested `install` and `public-read` regions in
`DocumentationExamplesTest.kt`. The website still has no reproducible extraction pipeline or
minimal quickstart compiled against published artifacts. These are separate pieces of work.
Do not advertise the pipeline as complete simply because source tests exist.

The HTTP client, media and control-plane client run on Java 21; the RDF4J adapter requires Java 25.
Building the repository requires Java 25, with Java 21 also needed for its consumer checks.
“Java 21 bytecode” by itself is insufficient setup guidance.

The site's exact SELECT returned three `e`, `name`, `start` bindings. Reading the first returned
event IRI yielded JSON-LD with an Event type and start date. Preserve both steps. The homepage's
claim that the SELECT response itself says `schema:Event` and `schema:startDate` needs correction:
the query contains those terms; the result bindings do not. The resource representation does.
The first two returned events are past dates, so this proves real event data, not an upcoming list.
Do not change the query and continue relying on the previous check.

The inventory found `docs/auth/identity.md` absent at v0.2.0. Other repository links need
target-and-anchor review and a choice between tagged release guidance and latest development.
The inventory checks only path presence, not a working public URL or its anchor.
